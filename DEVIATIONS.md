# DEVIATIONS.md — opencode API assumptions vs reality

Verified against **opencode 1.18.18** (docs at https://opencode.ai/docs/ + `@opencode-ai/plugin` type definitions via unpkg) on 2026-08-18.

| # | Assumption | Reality | What we do |
|---|------------|---------|------------|
| 1 | Plugin dir is `~/.config/opencode/plugin/` | Global plugin dir is `~/.config/opencode/plugins/` (**plural**). Project dir `.opencode/plugins/`. | Installer copies to `plugins/`. |
| 2 | Frontmatter `tools`/`permission` to make read-only agents | `tools` is **deprecated**; `permission` is the current mechanism. Values `allow`/`ask`/`deny`; keys match tool names (`edit`, `bash`, `read`, …). | Read-only agents use `permission: { edit: deny, bash: deny }`. `bash: deny` blocks mutating shell entirely (bash could write files), so recon/checker get no bash at all — strictly read-only, verified in acceptance gate 4. |
| 3 | Toast via a client method | `tui.toast.show` is an **event type** on the bus, not a plugin hook or documented client method. The `Hooks` type has no TUI hooks (`tui?: never`). | Session 1 plugin only logs events + writes state.json. Exact toast emit path (bus event publish vs TUI control API) to be resolved in session 2; candidate: TUI control endpoints (`GET /tui/control/next`, `POST /tui/control/response`). |
| 4 | Plugin context includes `directory` and shell helper | Confirmed: `{ client, project, directory, worktree, experimental_workspace, serverUrl, $ }` where `$` is Bun's shell. | Used as-is. |
| 5 | Hooks `event`, `tool.execute.before/after` exist | Confirmed. Full hook list in `@opencode-ai/plugin`: `dispose`, `event`, `config`, `tool`, `auth`, `provider`, `chat.message`, `chat.params`, `chat.headers`, `permission.ask`, `command.execute.before`, `tool.execute.before`, `tool.execute.after`, `shell.env`, `tool.definition`, plus `experimental.*` (chat.messages.transform, chat.system.transform, provider.small_model, session.compacting, compaction.autocontinue, text.complete). | We use `event` only in session 1. |
| 6 | `opencode serve` + SSE + `@opencode-ai/sdk` | Confirmed. Default port 4096, `GET /event` SSE starting with `server.connected`. SDK generated from the OpenAPI spec at `/doc`. | Dashboard (session 3) will use the SDK. |
| 7 | `subagent_depth` in opencode.json | Confirmed (default 1, we set 2). | Installer merges it. |
| 8 | Command frontmatter `description`, `agent`, `model`, `subtask` | Confirmed. `$ARGUMENTS`/`$1…`, `` !`cmd` `` and `@file` substitutions exist. | Used as-is. |
| 9 | Agent `mode: primary` joins Tab cycle | Confirmed by docs (primary agents are Tab-switchable next to build/plan). | `GIGGA` is `mode: primary`. |
| 10 | Agent model placeholder must be machine-rewritable | YAML frontmatter can't hold raw HTML comments as values. | Workers carry a valid default `model:` line with a trailing YAML comment containing the marker `<!-- set by GIGGA-config -->`; GIGGA-config finds lines matching `model: ... # <!-- set by GIGGA-config -->` and rewrites them. |
| 11 | `edit: deny` blocks only the edit tool | Verified empirically: with `permission: {edit: deny, bash: deny}`, a subagent's tool list shrinks to `read`, `grep`, `glob`, `webfetch`, `skill` — no write/edit/bash at all (the write tool is governed by the `edit` permission key). | `edit: deny` + `bash: deny` is sufficient read-only enforcement (acceptance gate 4, opencode 1.18.18). |
| 12 | (API testing note) `POST /session` takes `agent`, not `agentID`; `POST /session/:id/message` ignores `agentID` | A subagent-mode agent requested as session agent silently falls back to `build` with full permissions — misleading when testing read-only agents. | Tests must invoke recon/checker as real subagents (task tool / @-mention) or via a `mode: all` test agent. |
| 13 | Question reply via session-scoped endpoint | `POST /session/{id}/question/{qid}/reply` returns **200 but does not resolve the question tool**. The **global** `POST /question/{requestID}/reply` (body `{"answers":[["label"]]}`) works and emits `question.replied`. | E2E driver answers via the global endpoint. |
| 14 | Toast mechanism | `POST /tui/show-toast` (`{message, variant, title?, duration?}`) on the opencode server broadcasts a `tui.toast.show` bus event that the TUI renders. The plugin receives `serverUrl` in its input and POSTs there. | Plugin signals question-pending this way. |
| 15 | Bell | No HTTP/TUI API emits a terminal bell. The plugin writes `\x07` to `/dev/tty` (works when the server shares the TUI's controlling terminal; headless `opencode serve` fails gracefully and logs the skip). | Implemented with try/catch fallback; gated on config `sound`. |
| 16 | Plugin `event` hook input shape | The hook receives `{ event: Event }` — the bus event (`{type, properties}`) is nested under `.event`, not passed directly. (Session-1 skeleton logged `undefined {}` because of this.) | `handleEvent(input.event)`. |
| 17 | Driving a specific agent via API | A session created with `agent: "GIGGA"` still executed prompts as `build` until the **prompt body** also carries `"agent": "GIGGA"` (then `message.info.agent` reports `GIGGA`). | E2E driver passes `agent` on every `prompt_async`. |
| 18 | Task/subagent lifecycle events | `message.part.updated` with `part.tool === "task"`: `state.input.subagent_type/description/prompt` on `running`; `state.output` contains `<task id="ses_…" state="completed">` on completion (this is how the subagent session ID is learned). Subagent `session.created` carries `info.parentID`. `todowrite` is the todo tool. | Plugin tracks workers from these. |
| 19 | opencode resolves cwd to the git root | A session pointed at `GIGGAv3/test/fixtures` (nested dir of the GIGGAv3 repo) actually ran with cwd = GIGGAv3 root. | E2E fixtures are copied into a standalone `git init` repo before each run. |
| 20 | Session storage location for disk fallback | opencode 1.18 persists sessions/messages/parts in **SQLite** (`~/.local/share/opencode/opencode.db`, tables `session`/`message`/`part` with JSON `data` columns), not per-project JSON files. | Dashboard reads it read-only via node's built-in `node:sqlite` (experimental in node 22, guarded by try/catch). |
| 21 | Model listing | `GET /config/providers` on the opencode server returns authed providers with their models; `opencode models` CLI is the fallback. | `listModels()` in dashboard/lib/shared.mjs. |
| 22 | Server discovery for the dashboard | The plugin receives `serverUrl` in `PluginInput`; there is no discovery endpoint. | Plugin writes `~/.config/opencode/GIGGA/server.json` (`{url, directory, pid, updatedAt}`) on load; the dashboard health-checks it. |
| 23 | Enforcing the question-round cap | `permission.ask` does **not** fire for the `question` tool (and `question: ask` hangs headless). `tool.execute.before` cannot deny a call — it can only mutate `output.args`. | At the (cap+1)-th question tool call in a GIGGA session, the plugin empties `args.questions`; the orchestrator's prompt tells it to proceed with assumptions when that happens. Batching caveat: a model issuing many separate question calls in ONE round can hit the cap early (under-asking, never over-asking). |
| 24 | Agent-level scoped bash | Permission patterns match the command string (glob style); verified `permission.bash: {"node *shared.mjs*": allow, "*": deny}` parses in the agent config. | GIGGA-config gets bash only for the shared CLI + `opencode models`. |
| 25 | TUI child-session navigation | `session_child_cycle` (default `→`), `session_child_cycle_reverse` (`←`), `session_parent` (`↑`) exist natively; documented in README rather than shipping a tui.json (defaults already work). | Terminal equivalent of the dashboard click-through. |
| 26 | Sub-subagents (depth 2) | Despite `subagent_depth: 2` in config, subagents on 1.18.18 have **no task tool** (direct probe: a worker instructed to spawn one reports `NO-TASK-TOOL`); `permission: {task: allow}` in worker frontmatter did not surface the tool either. | COMPLIANCE row 12 escalated. Worker prompts + config kept ready for a future opencode version. |
| 27 | TUI sidebar | The TUI has a toggleable sidebar (`sidebar_toggle`, default `<leader>b` = ctrl+x b) listing sessions by title; `PATCH /session/{id}` `{title}` sets titles (live-updatable, ~70-char cap; titles are plain text — emoji keep their native colors, which is the only way to get red/yellow/green). BUT this only works when an opencode HTTP server is reachable (see #29); and the claim "no plugin API renders custom sidebar content" was wrong — the TUI plugin slot API does (see #29). | Serve/attach mode: the plugin renders an animated progress tree in row titles via a 1-second sweep (one batched pass, PATCHes only changed rows): the GIGGA row carries a 6-step phase bar with a pulsing current step plus one traffic-light dot per subagent (🟢 done · ❌ failed · 🟡 running · 🔴 spawning); every child row carries a `├─`/`└─` connector, its status dot, a braille spinner, and a ticking m:ss clock — frozen to `✓ m:ss`/`✗ m:ss` on completion; the orchestrator row flashes 🎉 then settles to `✓ … done · mm:ss · N workers`. Spinner/pulse/flash phases derive from wall-clock time so concurrent plugin instances compute identical titles (no flapping). Plain TUI mode: superseded by the slot widget (#29). |
| 28 | Plugin export shape | `~/.config/opencode/plugins/*` is auto-discovered, but the loader (`getLegacyPlugins`, verified v1.18.18 source) iterates EVERY module export, throws `Plugin export is not a function` at any non-function export, and CALLS every exported function as a plugin with the PluginInput object — helpers that touch their string args then throw (e.g. `path.basename` → `The "path" property must be of type string, got object`). Both error signatures confirmed in opencode.log. | GIGGA.ts exports exactly ONE function (`GiggaPlugin`); all helpers (incl. `projectStatePath`) are module-private. Rule for contributors: never add named exports to the plugin file — test helpers through behavior, not imports. |
| 29 | TUI hosts an HTTP server at plugin `serverUrl` | In plain TUI mode opencode listens on **no port** (`ss -tlnp` shows no socket for the TUI process) — `PluginInput.serverUrl` points at the default `http://localhost:4096/` with nothing behind it, so `PATCH /session/{id}` titles and `POST /tui/show-toast` always fail ("Unable to connect"; observed every 1s in events.log during runs). The real UI surface in the TUI is the **TUI plugin API** (`@opencode-ai/plugin/tui`, registered via the `plugin` array in `tui.json`): `api.slots.register({ slots: { sidebar_content(ctx, {session_id}) } })` renders Solid/OpenTUI JSX in the sidebar (`solid-js`/`@opentui/*` imports are provided by the runtime — no local node_modules needed, proven by tps-plugin.tsx), `api.state.path` exposes `{state, config, worktree, directory}`, and `api.ui.toast` / `api.attention.notify({notification, sound: {name: "question"\|"done"\|"error"\|…}})` deliver in-TUI toasts plus cross-platform desktop notifications + sounds (focus-aware; user-tunable via `attention` in tui.json). | The backend plugin probes `serverUrl/global/health` once at load and skips the title sweep + HTTP toasts when unreachable (title tree kept for `opencode serve` attach). `plugins/GIGGA-sidebar.tsx` (installed to `plugins/`, registered in `tui.json`) renders the same progress tree in the sidebar by polling the per-project state.json (1s, mtime-gated) and raises toast + attention notifications on question-pending / done / failed transitions (first poll is a baseline — no stale alerts). |
| 30 | Model ids are `provider/name` with a simple name segment | Local providers key models by **file path** — e.g. `llamacpp//home/user/.cache/huggingface/…/model.gguf` (observed in the wild; contains slashes). Also: `chat.params` fires per LLM call with the RESOLVED model (`input.model.{providerID,id}`) and the agent name; TUI model selection is global, so the last non-GIGGA call's model is the user's current selection (GIGGA sessions themselves run on tier models post-config — must be skipped). | Tier validation accepts `provider/\S+` (path-like ids legal); the plugin records the prompt-time model to `GIGGA/last-model.json` via `chat.params` (non-GIGGA agents only) so first-run auto-config and `/GIGGA-setup` default all tiers to it. |
| 31 | Sidebar slot props are static | The `sidebar_content` slot receives `props.session_id` — the session the user is currently VIEWING in that TUI instance — so a widget can scope itself to the session that owns the run. Combined with the state file's `orchestrator` / `agents[].sessionId` / per-session `createdAt` (recorded at `session.created`), the widget distinguishes: viewed session in the run → full tree; fresh GIGGA session (created after the run started, not yet bound) → `READING` placeholder; anything else → hidden. New activity in a terminal-phase (done/failed) run's session resets the run — guarded by >3s since `doneAt` so a late update of the final message can't wipe the just-finished state. | GIGGA-sidebar.tsx renders per viewed session; plugin/GIGGA.ts records `sessions[].createdAt` and resets on continuation. |
